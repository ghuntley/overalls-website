Architecture

Overalls is a monorepo of small services, each named after something or someone, with one NixOS deployment that wires them together. Marshall holds the record of what should exist. Lilly hosts make it physically true and report back. The other services sit at the edges: SSH, DNS, egress, inference, integrations, clients and notifications.

Control plane and hosts

You can run multiple Marshall instances against a shared PostgreSQL. Machine capacity is admitted atomically, so concurrent requests can't overbook a host. Every lifecycle change is a durable operation with an audit trail. Each host's Lilly dials out to Marshall with its own revocable credential, sends capacity reports and receives commands. A generation fence stops a delayed launch from starting a guest after a stop has already been requested.

Regions

We recommend running Marshall in a single region. Its instances share one PostgreSQL, and admission, sharing and lifecycle decisions all depend on that database, so keep them close to it. Run several instances in that region for high availability.

Lilly hosts connect to Marshall over HTTPS, so you can put hosts in every region where your developers work. Cross-host cloning and relocation also require reachable, authenticated transfer SSH endpoints.

Where the traffic goes depends on how you connect. SSH, VS Code over Remote-SSH, shared web apps and the browser editor enter through Audi on the machine's own host. Their data stays in that region, while Marshall authorises access. The browser terminal is relayed through Marshall, over the connection the host dialled out, so it pays the round trip to the control-plane region.

A machine's life

A machine is an identity first and a process second. Its UUID, name, private address, sharing and disk outlive any particular Firecracker process, so stopping, resizing and relocating it don't create a new machine. Running relocations involve downtime. Cloning creates an independent machine: the copy is private, gets a new identity, name and address, and starts without the source's RAM.

From inside a guest

Guests reach the outside world through services that can check, cache and record the traffic. Brady handles public HTTP and HTTPS, Ziggy handles inference, and Galileo handles integrations. Enrico serves Marshall's repository browser. Lateral traffic between guests and to private address ranges is blocked by Lilly's nftables policy. The locked-down customer profile removes outbound networking entirely.

Principles

  • Declared, reviewed, then applied. Hosts, images, users and secret recipients live in Git. Hosts install from a reviewed plan and update from a pinned branch.
  • Make it your own. Your fork is yours to change. Patch a component, pin a package or add tools to the guest images with a Nix overlay ↗ rather than carrying a long-lived fork of the code.
  • Secrets never travel in the clear. SOPS and age documents are encrypted to each host's SSH-derived key and to named recovery users. Private keys are generated where they're used.
  • Authority is checked at execution time. Cedar policies are evaluated when each action runs, not when a page was loaded, so revoked access takes effect on pages that are already open.
  • Uncertainty is explicit. If a request might not have reached a host, the system asks for deliberate reconciliation rather than guessing.
